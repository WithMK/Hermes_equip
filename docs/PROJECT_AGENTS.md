# 프로젝트별 Agent 배정 — 1~4단계 (0.10.0)

배정 편집·저장과 실제 업무 실행을 연결합니다. 서버는 `--enable-specialists`로
실행해야 합니다. custom 모드의 유효한 설정은 다음 업무가 실행을 시작할 때 적용됩니다.
기존 방식(legacy)은 기존 기본 Agent 선택을 유지합니다. GET의 runtime_applied는
현재 설정의 적용 가능 여부이며, 특정 업무에 적용된 설정은 업무 결과의 agent_assignment로 확인합니다.

## 실행 정책

- 기본 담당 Agent를 먼저 호출합니다. 이 호출은 추가 위임 횟수에 포함하지 않습니다.
- 추가 위임은 기존 요청 유형별 계획과 프로젝트의 활성 배정·allow_delegation의 교집합입니다.
  기본 담당 역할은 중복 호출하지 않고 max_delegations까지 순서대로 실행합니다.
- 마지막 수행 Agent의 검증된 응답이 최종 답변입니다. 사용자 지침은 역할과 도구 권한을 확장하지 않습니다.
- 한 프로젝트 안에서는 역할별 활성 배정을 하나만 지원합니다. 여러 프로젝트는 같은 역할의
  서로 다른 프로필을 사용할 수 있습니다. LLM이 임의의 팀을 생성하는 방식은 아닙니다.
- 위임을 끄면 기본 담당만 실행합니다. 기본 담당의 allow_delegation은 최초 호출을 막지 않습니다.
- custom 모드는 검색 근거를 사용하는 기존 전문 Agent들로 실행합니다. 근거가 없으면
  기존 no_evidence 응답을 반환하며, 기본 담당의 역할에 맞는 근거가 없으면 명시적으로 실패합니다.
- 대기열 등록 시점이 아니라 **실행 시작 시점**의 배정과 공통 Agent 프로필/버전을 고정합니다.
  시작 후 수정·비활성화는 진행 중인 업무에 영향을 주지 않고 다음 업무에 적용합니다.
- 시작 시 담당이 비활성·삭제·연결 미설정 상태라면 다른 Agent로 대체하지 않고 오류를 표시합니다.
  대기 중 프로젝트가 보관 상태로 바뀐 경우에도 실행하지 않습니다.

A/O 화면과 OpenWebUI의 프로젝트 모델(`ao/<domain>/<workspace>/project/<id>`)은
동일한 작업 큐와 배정 정책을 사용합니다. 일반 CLI의 직접 실행에는 웹 프로젝트 배정을
자동 적용하지 않습니다. 실행 결과의 Agent 실행 이력에서 배정 버전·기본 담당·실제 호출된
프로필 ID/버전을 확인할 수 있습니다. 시작 스냅샷은 `.web.db`에 영속 저장됩니다.

## 화면 사용

프로젝트 선택 → `프로젝트 Agent 배정`에서 등록된 Agent를 선택해 배정 추가합니다.
프로젝트별 구성 모드에서는 활성 Agent를 기본 담당으로 지정하고, 각 Agent의 역할 설명·
추가 지침·사용 여부·자동 위임 허용 및 최대 위임 횟수를 설정한 뒤 저장합니다.
비활성 공통 Agent는 비활성 배정으로 추가됩니다. 실제 사용을 준비하려면 먼저 기존
Agent 관리 화면에서 시험 호출 및 활성화를 완료해야 합니다.
기본 활성화는 기존 역할별 기본 담당을 교체합니다. `프로젝트 전용 활성화`는 기존 기본
담당을 유지하고 해당 프로필을 추가 활성화합니다. 같은 역할의 프로젝트 전용 Agent를
여러 개 만들 수 있습니다. 기존 방식의 실행은 이 프로젝트 전용 프로필을 자동 선택하지 않습니다.

편집 내용은 자동 새로고침으로 덮어쓰지 않습니다. 프로젝트 전환·페이지 종료 시
저장하지 않은 변경을 확인합니다. 저장 충돌 시 입력을 보존하며 `저장된 설정 다시
불러오기`로 서버의 최신 설정을 다시 읽을 수 있습니다. 이 동작은 편집 내용을 버립니다.
보관 프로젝트와 Agent 관리 연결이 없는 구성은 읽기 전용입니다.
배정 해제는 Agent 공통 프로필을 삭제하지 않습니다.

검증 명령:

```sh
npm install --prefix /tmp/ao-ui-test jsdom@26.1.0
NODE_PATH=/tmp/ao-ui-test/node_modules python tests/run_assignment_ui_smoke.py
```

이 검증은 실제 정적 화면 스크립트와 HTTP API를 사용해 추가·편집·저장·프로젝트 분리·
편집 보호·충돌 복구·배정 해제·보관 상태를 검사합니다. jsdom은 개발 검증용이며 운영
설치에 Node/npm이 필요하지 않습니다. 브라우저 레이아웃과 기본 확인창은 대상 PC에서 확인합니다.

## API

- GET `/v1/projects/{project_id}/agent-assignments`: 저장 설정 및 현재 Agent 유효성 조회
- PUT 같은 경로: 전체 설정 교체. 기존 웹 API의 동일 출처 정책과 `X-AO-Request: 1` 필요
- 최초 저장은 version 0, 이후에는 조회한 배정 version 전달. 충돌은 409
- 활성 프로젝트에서만 변경 가능. 보관 프로젝트는 조회만 가능
- Agent 관리 연결이 없는 경우 조회는 가능하며 저장은 503
- GET `/v1/projects/{project_id}/agent-assignments/export`: 저장된 설정 JSON 다운로드
- POST `/v1/projects/{project_id}/agent-assignments/import-preview`: 대상 버전과 가져올 JSON 비교 (쓰기 없음)

## JSON 가져오기·내보내기

프로젝트 화면에서 `저장된 배정 JSON 다운로드`를 누르면 이식 가능한 설정을 받습니다.
이 파일에는 프로젝트 ID, 배정 저장 버전, 공통 Agent 프로필/주소/인증키가 포함되지 않습니다.
Agent는 ID로 참조하므로 다른 서버에서는 해당 ID의 Agent를 먼저 등록·시험·활성화하세요.

```json
{
  "format": "hermes-project-agents",
  "format_version": 1,
  "configuration": {
    "schema_version": 1,
    "mode": "legacy",
    "default_agent_id": "",
    "agents": [],
    "delegation_enabled": true,
    "max_delegations": 4
  }
}
```

파일을 직접 수정한 뒤 UI의 파일 선택 또는 JSON 붙여넣기로 가져올 수 있습니다.
UI 입력 제한은 UTF-8 기준 1 MiB입니다. `변경 내용 비교`로 기본 담당·위임 정책·Agent
추가/변경/제거를 확인하고 `확인한 설정 적용`을 눌러 저장합니다. 전체 배정을 교체하며
병합 방식은 아닙니다. 내보내기는 편집 중인 초안이 아닌 서버에 저장된 설정을 사용합니다.

비교 API body는 `{"version": 대상의현재버전, "document": 위JSON}`입니다.
응답은 정규화한 configuration, changes, validation_issues, can_apply를 포함합니다.
비교는 저장하지 않습니다. 변경이 없거나 오류가 있으면 UI 적용 버튼을 비활성화합니다.
적용은 기존 PUT API에 비교 응답의 version/configuration을 전달하고 Agent 상태와 버전을
다시 검증합니다. 비교 뒤 다른 사용자가 저장했다면 409, Agent를 비활성화했다면 422입니다.
UI에서 JSON이나 배정 편집 내용을 바꾸면 이전 비교 결과는 무효화됩니다.
실패 시 JSON 입력을 유지합니다. 필요한 입력을 복사해 둔 뒤 저장된 설정을 다시 불러와
최신 버전 기준으로 비교하세요. 보관 프로젝트는 내보내기만 가능하며 변경할 수 없습니다.

## PUT 설정 예시

```json
{
  "version": 0,
  "configuration": {
    "schema_version": 1,
    "mode": "custom",
    "default_agent_id": "document-agent",
    "agents": [
      {
        "agent_id": "document-agent",
        "assignment": "문서 검토",
        "instructions": "근거 누락을 확인한다.",
        "enabled": true,
        "allow_delegation": true
      }
    ],
    "delegation_enabled": true,
    "max_delegations": 4
  }
}
```

배정 최대 32개, Agent ID 중복 금지, 지침 최대 4,000자, 추가 위임 횟수 0~8입니다.
위임 활성 시 횟수는 1 이상이어야 합니다. custom 모드는 활성 배정 중 기본 담당을
지정해야 합니다. 활성 배정은 현재 사용 가능한 활성 Agent만 참조할 수 있습니다.
비활성 배정도 존재하는 Agent ID를 참조해야 합니다. 서비스 주소·인증키·새 도구 권한은
입력할 수 없습니다. 역할 설명은 표시/지침용이며 실행 도구를 생성하지 않습니다.

배정 저장은 Agent 공통 프로필을 변경하지 않습니다. 이후 공통 Agent가 비활성화되거나
삭제되면 GET의 validation_issues에 표시하고 원래 배정은 보존합니다. 대체 Agent를
자동 선택하지 않습니다. 역할별 기본 활성 Agent와 프로젝트 전용 활성 Agent를 구분합니다.

배정은 기존 `.projects.db`의 별도 테이블에 저장합니다. 프로젝트 기본 정보 버전과
배정 버전은 독립적입니다. 변경 이력은 프로젝트 history에 남습니다.
schema 1→2 자동 마이그레이션을 수행하므로 업데이트 전에 상태 DB를 백업하세요.

1. 프로젝트별 설정 저장·검증 API — 완료
2. 프로젝트 화면 배정 편집 — 완료
3. 실행 시작 시 설정 고정 및 실제 위임 적용 — 완료

대상 PC에서는 기존 상태 DB를 백업하고 0.10.0 변경을 배포한 뒤 다음을 확인하세요.

1. 서버를 `--enable-specialists`로 실행하고 Agent 시험 호출/활성화 확인.
2. 같은 역할의 다른 프로필을 프로젝트 전용으로 활성화해 프로젝트 A/B에 각각 배정.
3. 각 프로젝트에 근거 문서를 준비하고 같은 요청을 실행해 결과의 Agent ID/배정 버전 확인.
4. A의 JSON을 내보내 B에서 비교·적용하고, B의 다음 업무부터 변경되는지 확인.
5. OpenWebUI에서 프로젝트 모델을 선택해 동일한 배정으로 실행되는지 확인.
6. 서버 재시작 후 배정/실행 이력 유지, 보관 프로젝트 읽기 전용, 화면 배치/다운로드 확인.

자동 테스트는 합성 RAG/Chat과 실제 HTTP API를 사용합니다. 실제 C/M·llama.cpp의 답변
품질 및 브라우저 시각 검증은 대상 PC에서 수행합니다. EquipmentRAG와 C/M의 API 변경은 없습니다.
